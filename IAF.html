Abstract

As AI systems increasingly participate in software creation, the gap between human intent and AI implementation has become a fundamental bottleneck. Current AI-assisted development tools operate within a translation chain—human intent → natural language description → code generation—where each step introduces information loss, resulting in systematic misalignment between what humans want and what AI produces. This paper proposes the Intent Alignment Framework (IAF), a formal specification for expressing, verifying, and evolving human intent in a mathematically rigorous manner. IAF defines intent as a triple of structured spaces (P,N,A)—positive constraints, negative constraints, and AI autonomy—built from a finite set of 27 intent atoms and seven composition operators. We formalize intent verification as a simulation relation (allowing AI to refine human intent) and intent evolution as a weakly invertible algebraic transformation system. The framework introduces a layered verification protocol (L0–L3) ranging from syntactic checks to formal proofs, and a refinement order on intents that supports incremental specification. The framework provides a foundation for moving from code-centric development to intent-driven development, where humans define the intent space and AI autonomously explores the implementation space.

Keywords: Human-AI collaboration, intent alignment, formal specification, intent-driven development, program synthesis, requirement engineering, simulation relation, refinement order

1. Introduction

1.1 Background and Motivation

The rise of large language models has dramatically improved AI's ability to generate code. However, a persistent and fundamental problem remains: the systematic misalignment between human intent and AI output. This misalignment is not primarily a limitation of AI capability—it is a structural problem inherent in the current development paradigm.

In traditional software engineering, humans express requirements through natural language documents (PRDs, user stories), which are then translated by developers into technical specifications, and finally into code. Each translation step introduces information loss. When AI replaces the developer in this chain, the same lossy translation occurs: human intent is compressed into a prompt, and the AI reconstructs an implementation from that compressed representation.

The core issue is that natural language is inherently ambiguous, while software requirements demand precision. The gap between these two modes of expression is the root cause of the "AI doesn't understand what I want" problem.

1.2 Problem Statement

We formalize the problem as follows:

Given a human intent H and an AI-generated implementation I, how can we guarantee that I faithfully realizes H?

Current approaches rely on iterative refinement through natural language feedback, which suffers from: - Ambiguity accumulation: Each round of feedback may introduce new ambiguities - Lossy compression: The original intent is progressively distorted - No verification guarantee: There is no formal way to confirm alignment

1.3 Contributions

This paper makes the following contributions:

  1. A formal definition of intent as a triple of structured spaces (P,N,A) with well-formedness conditions
  2. A complete set of 27 intent atoms covering existence, relationship, behavior, constraint, preference, and uncertainty
  3. Seven composition operators with denotational semantics and verified algebraic properties
  4. A layered verification protocol (L0–L3) replacing strict isomorphism with simulation relations
  5. A refinement order (⊑) on intents supporting incremental specification
  6. An algebraic model of intent evolution with weak invertibility supporting version control and rollback
  7. A multi-modal expression layer mapping natural human expression to formal intent

2. Related Work

2.1 Requirement Engineering

Traditional requirement engineering has long recognized the gap between stakeholder intent and technical specification. Approaches include use cases, user stories, and acceptance criteria. However, these methods were designed for human-to-human communication and assume shared background knowledge—a assumption that breaks down in human-AI interaction.

2.2 Formal Methods in Software Engineering

Formal specification languages (Z, B, TLA+, Alloy) provide mathematical rigor for system specification. However, they require specialized expertise and are impractical for non-expert users. IAF differs by being designed as an intermediate representation—not meant to be written directly by humans, but as the target of multi-modal intent parsing.

2.3 Program Synthesis and AI-Assisted Development

Program synthesis aims to generate programs from specifications. Recent advances in LLM-based code generation (Copilot, Codex, Cursor) have made this more practical but still rely on natural language prompts. IAF provides a structured specification format that could serve as an intermediate representation between natural language prompts and code generation.

2.4 Type Theory and Dependent Types

Dependent type systems allow types to encode program properties. The "propositions as types" paradigm connects logical propositions with type signatures. IAF's intent atoms draw inspiration from this tradition, particularly the use of temporal logic operators and quantifiers.

2.5 Simulation Relations in Formal Verification

Simulation relations are a standard technique in formal verification for relating systems of different abstraction levels. Unlike bisimulation (which requires mutual simulation), simulation allows the implementation to be more detailed than the specification—exactly the property we need for human-AI intent alignment where AI may reasonably refine human intent. IAF adopts this technique for intent verification.

3. The Intent Alignment Framework

3.1 Design Principles

IAF is built on six foundational principles:

Principle Description Mathematical Analogy
Unambiguity Same intent expression yields identical understanding by human and AI Unique truth value of mathematical propositions
Verifiability Any alignment result can be independently verified Reproducibility of mathematical proofs
Composability Simple intents compose into complex intents Closure of algebraic structures
Progressiveness Intent converges from vague to precise through iteration Limits and approximation
Traceability Every evolution of intent is fully recorded Weak reversibility of algebraic transformations
Low Friction Human expression cost must be minimal Natural isomorphism (intuitive mapping)

3.3 Intent Spaces

An intent is defined as a triple of three structured spaces:

Intent=(P,N,A)

3.3.1 Positive Space (P)

P=a∣a is an intent atom that must be satisfied

The positive space defines what the system must be. All atoms in P are hard constraints—none can be omitted.

3.3.2 Negative Space (N)

N=¬a∣a is an intent atom that must be avoided

The negative space defines what the system must not be. Each element in N is the logical negation of an atom that must not hold.

v0.2 change: N-space elements are now explicitly written as ¬a (negated atoms). This makes the semantics unambiguous: for any n=¬a∈N, the implementation must satisfy ¬a (i.e., a must not hold).

Example: N=¬Prefer(Complex, Simple),¬Prefer(Slow, Fast),¬Prefer(Cold, Warm) — the system must not be complex, slow, or cold.

3.3.3 Autonomy Space (A)

A=x∣x is left to AI's autonomous decision

The autonomy space defines the AI's degree of freedom. A larger A gives AI more creative space; a smaller A means tighter human control.

3.3.4 Well-formedness Conditions (v0.2 new)

Not every triple (P,N,A) is a valid intent. We define well-formedness as follows:

Definition 1 (Well-formed Intent): An intent I=(P,N,A) is well-formed if and only if:

  1. Syntactic consistency: P∩a∣¬a∈N=∅ — no atom appears in both P and N
  2. Semantic satisfiability: P∪¬a∣¬a∈N is satisfiable — there exists at least one implementation satisfying all positive constraints and avoiding all negative constraints
  3. Autonomy non-emptiness: ∀a∈A, there exists at least one choice s∈Choices(a) such that s⊨P∪¬a∣¬a∈N — every autonomy decision has at least one valid option
  4. Minimality: No p∈P is redundant — there is no p∈P such that (P∖p)⊨p

Rationale: Condition 2 (satisfiability) addresses a critical gap in v0.1. The original check P∩N=∅ only catches direct set intersection, but misses semantic contradictions like P=◻(Balance≥0) and N=¬◻(Balance≥0). Satisfiability checking can be automated using SMT solvers (e.g., Z3).

3.4.1 Denotational Semantics (v0.2 new)

We define the semantics of each operator using denotational semantics, mapping each operator to the set of implementations it admits.

Let \llbracketI\rrbracket denote the set of all implementations satisfying intent I.

Definition 2 (Parallel semantics):

\llbracketI1∥I2\rrbracket=I∣I⊨P1∪P2∧I⊭N1∪N2∧I respects A1∪A2

Definition 3 (Sequential semantics):

\llbracketI1→I2\rrbracket=I∣I⊨P1∧after(I1),I⊨P2∧I⊭N1∧after(I1),I⊭N2

where after(I1) denotes the state after I1's constraints are satisfied.

Definition 4 (Conditional semantics):

\llbracketCond(c,I1,I2)\rrbracket={\llbracketI1\rrbracketif c evaluates to true \llbracketI2\rrbracketif c evaluates to false

Definition 5 (Iterative semantics):

\llbracketI∗\rrbracket=⋃k=0∞\llbracketI\rrbracketk

where \llbracketI\rrbracket0 is the identity (no constraints) and \llbracketI\rrbracketk+1=\llbracketI\rrbracket∥\llbracketI\rrbracketk.

Definition 6 (Alternative semantics):

\llbracketI1⊕I2\rrbracket=\llbracketI1\rrbracket∪\llbracketI2\rrbracket

An implementation satisfies I1⊕I2 if it satisfies either I1 or I2. The shared constraints P1∩P2 and shared prohibitions N1∩N2 must hold in both branches.

Definition 7 (Exclusion semantics):

\llbracketI1∖I2\rrbracket=I∣I∈\llbracketI1\rrbracket∧I∉\llbracketI2\rrbracket

Definition 8 (Nesting semantics):

\llbracket⟨I⟩\rrbracket=\llbracketI\rrbracket

Nesting treats I as an atomic unit for composition purposes. The internal structure is preserved but not exposed to the outer composition.

3.4.2 Algebraic Properties (v0.2 corrected)

The composition operators satisfy the following algebraic laws:

Associativity (sequential):   (I₁ → I₂) → I₃ ≡ I₁ → (I₂ → I₃)
Commutativity (parallel):     I₁ ∥ I₂ ≡ I₂ ∥ I₁
Associativity (parallel):     (I₁ ∥ I₂) ∥ I₃ ≡ I₁ ∥ (I₂ ∥ I₃)
Idempotency (parallel):       I ∥ I ≡ I
Distributivity (conditional): Cond(c, I₁ ∥ I₂, I₃) ≡ Cond(c, I₁, I₃) ∥ Cond(c, I₂, I₃)
Commutativity (alternative):  I₁ ⊕ I₂ ≡ I₂ ⊕ I₁
Associativity (alternative):  (I₁ ⊕ I₂) ⊕ I₃ ≡ I₁ ⊕ (I₂ ⊕ I₃)

v0.2 change: The absorption law A ∥ (A → B) ≡ A → B has been removed. As identified in review, it is logically inconsistent with the idempotency law: setting B = A gives A ∥ (A → A) ≡ A → A, and by idempotency A ∥ A ≡ A, implying A ≡ A → A, which would mean sequential and parallel composition are equivalent for all intents—a contradiction. The absorption law does not hold universally and is only valid under specific preconditions (e.g., when A entails B's preconditions).

3.4.3 Conflict Definition (v0.2 new)

Definition 9 (Conflict): Two intents I1 and I2 are in conflict if:

Conflict(I1,I2)⟺(P1∩a∣¬a∈N2≠∅)∨(P2∩a∣¬a∈N1≠∅)∨SAT(P1∪P2∪¬a∣¬a∈N1∪N2)=false

That is, conflict occurs when: 1. I1's positive constraints violate I2's negative constraints, or 2. I2's positive constraints violate I1's negative constraints, or 3. The combined constraints are unsatisfiable (detected by SMT solver)

3.5 Refinement Order (v0.2 new)

We define a partial order on intents to support incremental specification.

Definition 10 (Refinement Order): For intents I1=(P1,N1,A1) and I2=(P2,N2,A2):

I1⊑I2⟺P1⊆P2∧N1⊆N2∧A2⊆A1

We say "I2 refines I1" (written I1⊑I2) when I2 has more constraints (larger P and N) and less autonomy (smaller A). Intuitively, I2 is a more specific version of I1.

Theorem 1 (Lattice Structure): The refinement order ⊑ forms a complete lattice with: - Least upper bound (join): I1⊔I2=(P1∪P2,N1∪N2,A1∩A2) - Greatest lower bound (meet): I1⊓I2=(P1∩P2,N1∩N2,A1∪A2)

Proof sketch: The join combines all constraints and intersects autonomy (most restrictive). The meet takes common constraints and unions autonomy (least restrictive). Both operations preserve well-formedness when the operands are well-formed and non-conflicting. □

Corollary (Monotonicity): If I1⊑I2, then any implementation satisfying I2 also satisfies I1. This is the fundamental property that makes refinement useful: refining an intent never invalidates a correct implementation of the original.

4. Verification Protocol

4.1 From Isomorphism to Simulation (v0.2)

The v0.1 verification protocol required structural isomorphism (H≅A), meaning a bijection between human and AI intent atoms. This requirement is too strong: it rejects cases where the AI reasonably refines the human's intent.

Example: Human intent requires Reachable(Home, Product). AI interprets this as Reachable(Home, Catalog) ∧ Reachable(Catalog, Product) — a valid refinement that introduces an intermediate Catalog entity. Under isomorphism, this fails because |PH|≠|PA|. Under simulation, it succeeds because the AI's intent implies the human's.

We replace isomorphism with simulation relation, a standard technique in formal verification.

4.2 Simulation Relation

Definition 11 (Simulation): Intent IA simulates intent IH (written IA▹IH) if and only if:

  1. Positive coverage: ∀p∈PH,∃p′∈PA such that p′⊨p (every human requirement is satisfied by some AI requirement)
  2. Negative coverage: ∀¬n∈NH,∃¬n′∈NA such that ¬n′⊨¬n (every human prohibition is respected by some AI prohibition)
  3. Autonomy preservation: AH⊆AA (AI has at least as much autonomy as the human specified)

Theorem 2 (Simulation preserves alignment): If IA▹IH, then any implementation satisfying IA also satisfies IH.

Proof: By Definition 11, every atom in PH is implied by some atom in PA, and every prohibition in NH is implied by some prohibition in NA. Any implementation satisfying all of PA and avoiding all of NA must therefore satisfy all of PH and avoid all of NH. Autonomy preservation ensures no additional constraints are imposed. □

Definition 12 (Refinement equivalence): IA∼IH⟺IA▹IH∧IH▹IA

Refinement equivalence is weaker than isomorphism but stronger than semantic equivalence, and it allows reasonable refinement.

4.3 Layered Verification Protocol (v0.2 new)

Rather than a single verification step, we propose a four-layer protocol that provides increasing guarantees at increasing cost:

Layer Method Decidability Guarantee Cost
L0: Syntax P∩a∣¬a∈N=∅, type checking ✅ Decidable Weak (structural) O(1)
L1: Structure PH⊆PA (set containment) ✅ Decidable Medium (coverage) O(n)
L2: Simulation IA▹IH (Definition 11) ⚠️ Semi-decidable Strong (semantic) O(n · SMT)
L3: Proof Formal proof IA≅IH ❌ Undecidable (in general) Strongest Manual

Practical recommendation: L0–L1 are always executed automatically. L2 is executed as best-effort using SMT solvers. L3 is reserved for safety-critical scenarios with manual proof assistance.

4.4 Verification Procedure

Step 1: Decomposition
    H → (P_H, N_H, A_H)  (human intent)
    A → (P_A, N_A, A_A)  (AI understanding)

Step 2: L0 Syntax Check
    Verify P_A ∩ {a | ¬a ∈ N_A} = ∅
    → Fail: report syntactic contradiction
    → Pass: continue

Step 3: L1 Structure Check
    Verify P_H ⊆ P_A and N_H ⊆ N_A and A_H ⊆ A_A
    → Fail: report missing atoms
    → Pass: continue

Step 4: L2 Simulation Check
    For each p ∈ P_H, find p' ∈ P_A such that p' ⊨ p (using SMT)
    For each ¬n ∈ N_H, find ¬n' ∈ N_A such that ¬n' ⊨ ¬n (using SMT)
    → Fail: generate diff report → enter correction loop
    → Pass: intent aligned ✓

Step 5: Scoring
    Compute alignment score (see §4.5)

4.5 Alignment Score (v0.2 minimax model)

The v0.1 scoring formula used a weighted sum, which allowed soft constraints to compensate for hard constraint violations. We replace this with a minimax model that ensures hard constraints are non-negotiable.

$$\text{AlignmentScore} = \underbrace{\min_{p \in P_{\text{hard}}} S(p)}_{\text{hard constraint gate}} \times \underbrace{\frac{\sum_{p \in P_{\text{soft}}} w_p \cdot S(p)}{\sum_{p \in P_{\text{soft}}} w_p}}_{\text{soft constraint average}}$$

where: - Phard = hard constraints (existence, invariants, atomicity, boundaries) - Psoft = soft constraints (preferences, weights) - S(p)∈0,1 is the satisfaction indicator (1 if satisfied, 0 if not) - wp is the weight of soft constraint p

Key property: If any hard constraint is unsatisfied (S(p)=0), the total score is immediately 0. Soft constraints can never compensate for hard constraint violations.

5. Intent Evolution

5.1 Algebraic Model

Intent is not static. We model evolution as a sequence of algebraic transformations:

$$\text{Intent}_0 = (P_0, N_0, A_0)$$ $$\text{Intent}_1 = \text{Intent}_0 \oplus \Delta_1$$ $$\text{Intent}_n = \text{Intent}_{n-1} \oplus \Delta_n$$

where ⊕ is the intent transformation operator and Δ is an incremental transformation.

5.2 Transformation Types

Transformation Notation Semantics Example Info-preserving?
Addition +a Add atom a +∃Payment ✅ Yes
Removal −a Remove atom a −R(Order,Invoice) ❌ No
Modification a↦a′ Atom a becomes a′ ◻(Balance≥0)↦◻(Balance≥−100) ✅ Yes
Promotion ↑a Elevate constraint level (refinement) Prefer(Fast)↦◻(ResponseTime<200ms) ⚠️ Partial
Demotion ↓a Lower constraint level (weakening) ◻(Secure)↦Prefer(Secure) ❌ No
Migration a↦A Move from constraint to autonomy −Reachable(Home,Profile)↦Autonomy(Profile) ❌ No

5.3 Transformation Properties (v0.2 corrected)

Weak Invertibility:  Intent ⊕ Δ ⊕ Δ⁻¹ ⊒ Intent  (for information-preserving Δ)
                     Intent ⊕ Δ ⊕ Δ⁻¹ ⊓ Intent   (for information-loss Δ)
Associativity:       (Intent ⊕ Δ₁) ⊕ Δ₂ = Intent ⊕ (Δ₁ ⊕ Δ₂)
Identity:            Intent ⊕ ∅ = Intent

v0.2 change: The original claim Intent ⊕ Δ ⊕ Δ⁻¹ = Intent (strong invertibility) is incorrect for all transformation types. We replace it with weak invertibility:

  • Information-preserving transformations (Addition, Modification): Intent⊕Δ⊕Δ−1⊒Intent — the result is a refinement of the original (may have additional side effects but never loses constraints).
  • Information-loss transformations (Removal, Promotion, Demotion, Migration): No guarantee of recovery. These are irreversible in general.

This matches the practical reality of version control: you can revert an addition, but you cannot fully undo a deletion that has already influenced downstream decisions.

5.4 Version Control

IntentGraph:
    v0 → v1 → v2 → v3
              ↘ v2' (branch)

Each transformation generates a new version. The system supports branching and merging. Every version has a complete verification report. Any historical version can be restored if the transformation chain to it consists only of information-preserving operations.

  3. Autonomy non-emptiness: Layout, ColorScheme, etc. have valid choices under ¬Prefer(Complex, Simple) ✅ (simple designs exist)

8. AI Implementation Protocol

8.1 Implementation Pipeline

Given Intent=(P,N,A), the AI generates an implementation through:

Step 1: Well-formedness Check
    Verify P ∩ {a | ¬a ∈ N} = ∅ (L0 syntax)
    Verify SAT(P ∪ {¬n | ¬n ∈ N}) using SMT solver (L0 semantic)
    → Fail: return diff report
    → Pass: continue

Step 2: Autonomy Space Exploration
    Search for optimal implementation within A
    Evaluate using preference function from P
    Filter using constraints from N

Step 3: Constraint Satisfaction
    Search implementation space under P constraints
    Find solutions satisfying all hard constraints

Step 4: Preference Optimization
    Optimize preference function among feasible solutions

Step 5: Implementation Generation
    Output executable system

Step 6: Formal Verification
    Verify I ⊨ P (implementation satisfies all positive constraints) — L1
    Verify I ⊨ N (implementation violates no negative constraints) — L1
    Verify I_A ▷ I_H (simulation check) — L2
    → Pass: deliver
    → Fail: return to Step 3

10. Discussion

10.1 Why Formalize Intent?

Mathematics is the only known communication protocol that can bridge cognitive gaps without ambiguity. It does not depend on culture, language, or experience. If two civilizations can communicate through mathematics, humans and AI can communicate through formalized intent.

10.2 Why Negative Space?

Human cognition has a well-documented characteristic: we often define things by what they are not. "Not like Pinduoduo" contains more actionable information than "make it simple." The negative space is not a compromise—it is a recognition of how humans actually think.

The v0.2 change to explicit ¬ prefix in N makes this even clearer: N=¬Prefer(Complex, Simple) explicitly states "the negation of preferring complex over simple must hold," which is equivalent to "complex must be avoided."

10.3 Why Autonomy Space?

If humans define everything, AI is merely an executor—and this framework would be no different from traditional programming. The autonomy space is AI's creative space, where it can exceed human imagination. A good intent framework does not constrain AI—it releases AI within boundaries.

10.4 Why Simulation Instead of Isomorphism? (v0.2)

Isomorphism requires exact structural matching: the AI must understand exactly what the human specified, no more and no less. But this is too strict for practical use. AI may reasonably refine human intent by introducing intermediate entities, splitting monolithic requirements into finer-grained ones, or choosing specific implementations for abstract specifications.

Simulation relation IA▹IH captures the right notion: the AI's understanding must cover the human's intent (every requirement is met, every prohibition is respected), but the AI is free to add detail. This is exactly the property we want.

10.5 Why Weak Invertibility? (v0.2)

The original claim that all transformations are invertible was too optimistic. Removing a constraint, demoting a hard constraint to a preference, or migrating a decision to AI autonomy—all of these lose information that cannot be recovered. Weak invertibility acknowledges this reality: only information-preserving transformations (addition, modification) are reliably reversible.

10.6 This Is Not Replacing Human Design

This framework does not ask humans to think less—it asks humans to think about the right things. Not "what tech stack" or "how to design the database," but "what should the system do," "what must it not do," and "where can I let go."

Humans define the intent space. AI explores the implementation space. This is division of labor, not replacement.

11. Conclusion

The Intent Alignment Framework v0.2 provides a rigorous formal foundation for human-AI intent communication. Key improvements over v0.1 include:

  1. Well-formedness conditions ensuring intents are logically consistent and satisfiable
  2. Simulation relation replacing isomorphism, allowing AI to reasonably refine human intent
  3. Layered verification protocol (L0–L3) providing practical guarantees at different cost levels
  4. Refinement order (⊑) supporting incremental specification with lattice structure
  5. Denotational semantics for all composition operators with verified algebraic properties
  6. Weak invertibility correctly characterizing which transformations are reversible
  7. Minimax scoring ensuring hard constraints are non-negotiable
  8. Unified symbol system eliminating ambiguities between atoms and spaces

IAF represents a step toward intent-driven development, where the bottleneck of translation loss between human intent and AI implementation is eliminated through formal specification. The ultimate goal is a development paradigm where humans define what they want, and AI autonomously generates systems that are mathematically guaranteed to satisfy those intentions.
